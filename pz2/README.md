Практична робота №2
Тема: Застосування принципів SOLID та патерну Dependency Injection у системі Task Management

Мета роботи
Дослідити порушення принципів проектування програмного забезпечення (зокрема SRP та DIP) на прикладі підсистеми управління завданнями, виконати рефакторинг коду із виділенням сервісного шару, реалізувати механізм Dependency Injection та покрити отримане рішення модульними тестами з використанням mock-обєктів.

Структура проекту

models.py — доменні моделі системи (User, Task, Project), визначені як дата-класи без сторонньої бізнес-логіки.

bad_task_manager.py — демонстраційний клас BadTaskManager, реалізований до рефакторингу. Містить явне порушення принципу єдиної відповідальності (Single Responsibility Principle): поєднує валідацію вхідних даних, персистентність (запис у файл) та пряму відправку email.

services.py — результат рефакторингу:

Визначено абстрактний базовий клас NotificationSender (контракт відправника).

Реалізовано конкретні стратегії надсилання: EmailSender та SmsSender.

Реалізовано сервіс TaskService, у який залежність NotificationSender впроваджується через конструктор (Constructor Injection).

test_task_service.py — набір модульних тестів на базі бібліотеки unittest із використанням unittest.mock.MagicMock для повної ізоляції тестування бізнес-логіки TaskService від каналів сповіщення.

Опис виконаного рефакторингу

Дотримання SRP: Логіку збереження, валідації та оповіщення відокремлено від самої сутності завдання. TaskService відповідає виключно за створення обєкта та координацію дій.

Дотримання DIP та застосування DI: Сервіс TaskService залежить від абстракції NotificationSender, а не від конкретних реалізацій відправників. Це дозволяє змінювати спосіб нотифікації користувача (Email/SMS) без модифікації коду самого сервісу.

Запуск та перевірка тестів

Виконання модульних тестів реалізовано стандартними засобами Python:

python -m unittest test_task_service.py

Усі тест-кейси перевіряють:

створення завдання за наявності призначеного виконавця та виклик методу send;

створення завдання без призначеного користувача (відсутність виклику send);

коректність виклику винятків при некоректних вхідних параметрах.
